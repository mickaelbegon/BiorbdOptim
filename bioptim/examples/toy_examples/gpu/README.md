# CusADi pendulum benchmark

This experimental benchmark evaluates whether
[CusADi](https://github.com/se-hwan/cusadi) can accelerate a real CasADi
function generated by bioptim.

It builds the basic bioptim pendulum OCP, extracts its `ForwardDyn` dynamics
function, generates and compiles a CUDA kernel, verifies the result against
CasADi on the CPU, and records:

- maximum numerical error;
- serial mapped CasADi CPU time;
- CusADi kernel time;
- GPU-resident wall time;
- end-to-end GPU time including CPU/GPU transfers.

CusADi evaluates many independent instances of a CasADi function in parallel.
This benchmark therefore measures a useful building block for batched
simulation, parameter sweeps, MHE, or parallel OCPs. It does **not** move IPOPT
or a complete bioptim solve to the GPU.

## Requirements

- Linux on x86-64;
- an NVIDIA GPU and a working driver;
- CUDA Toolkit 12.x, including `nvcc`;
- CMake 3.18 or newer;
- a CUDA-enabled PyTorch installation;
- a CusADi checkout;
- a working bioptim development environment.

CusADi documents CasADi 3.6.5 as its tested version. The code-generation-only
check also makes it easy to detect unsupported operations with the CasADi
version installed by the current bioptim environment.

## Run on a Linux GPU machine

From the bioptim repository:

```bash
git clone https://github.com/se-hwan/cusadi.git /tmp/cusadi
python -m pip install torch
python -m pip install -e /tmp/cusadi

python bioptim/examples/toy_examples/gpu/cusadi_pendulum_benchmark.py \
    --cusadi-root /tmp/cusadi \
    --batch-sizes 1,32,256,2048,16384 \
    --warmup 5 \
    --repeats 20 \
    --output cusadi_benchmark_results.json
```

The benchmark detects the GPU compute capability and compiles the generated
kernel for that architecture. This avoids the fixed `sm_86` compiler flag in
the current CusADi CMake generator, which would otherwise prevent the same
experiment from running reliably on both Tesla T4 (`sm_75`) and newer GPUs.

## Check code generation without a GPU

The compatibility and code-generation phase can run on macOS or a CPU-only
Linux machine. PyTorch and CUDA are not imported in this mode:

```bash
python bioptim/examples/toy_examples/gpu/cusadi_pendulum_benchmark.py \
    --cusadi-root /tmp/cusadi \
    --codegen-only
```

Successful code generation means that CusADi implements every scalar CasADi
operation used by this dynamics function. It does not validate CUDA
compilation, numerical equivalence, or performance.

## Compile without a GPU

On a CPU-only Linux machine with the CUDA Toolkit installed, the generated
kernel can also be compiled without an NVIDIA device or driver:

```bash
python bioptim/examples/toy_examples/gpu/cusadi_pendulum_benchmark.py \
    --cusadi-root /tmp/cusadi \
    --compile-only \
    --cuda-architectures 75,86
```

This produces `build/libForwardDyn.so` for Tesla T4 (`sm_75`) and Ampere
(`sm_86`). Loading the library, validating its numerical output, and measuring
performance still require a CUDA-capable GPU.

## GitHub Actions

Every push to the experiment branch runs the code-generation check on a
standard Linux runner, installs a minimal CUDA 12.6 compiler, builds the
generated source for `sm_75` and `sm_86`, and uploads both `ForwardDyn.cu` and
`libForwardDyn.so`.

The GPU benchmark job defaults to a self-hosted runner labelled `gpu`:

```text
["self-hosted", "linux", "x64", "gpu"]
```

For a GitHub-hosted GPU larger runner, pass its configured runner name as a
JSON string instead, for example:

```text
"pyomeca-gpu-t4"
```

There are two ways to start it:

- once the workflow exists on the repository default branch, use
  `workflow_dispatch` and its `runs_on` input;
- while testing this feature branch, define the repository variable
  `CUSADI_GPU_ENABLED=true`, optionally set `CUSADI_GPU_RUNS_ON` to the JSON
  runner labels, and push to `codex/issue-1094-cusadi-gpu`.

The repository-variable gate prevents a push from waiting indefinitely when
no GPU runner is registered.

The workflow uploads the JSON measurements as an artifact.
